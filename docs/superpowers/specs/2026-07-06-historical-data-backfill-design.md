# 2018-2021 历史数据补数设计

## 背景

本次目标是基于 `任务/数据更新v2.py` 和 `任务/米筐数据更新.py`，补齐本地 `E:\working\stock_data` 中 2021 年之前的历史数据。当前已验证：

- `gm_stock_all_data`、`15min_stock_data_dir`、`15min_stock_data_right_dir` 从 `2021-01-04` 开始，`2018-2020` 缺失。
- `rq_stock_all_data`、`rq_adj` 从 `2021-01-04` 开始，`2018-2020` 缺失。
- `rq_stock_all_data` 的现有 2021 数据混入了指数/非股票代码，典型样本包括 `SHSE.000001`、`SHSE.H50066`、`SZSE.980001`，且春节、国庆假期存在少量非股票分区。
- 根因是 `米筐数据更新.py` 的 `fetch_day_range(..., rq_codes=...)` 虽然接收股票池，但 DDB 日线查询没有真正使用 `rq_codes` 过滤。

用户确认采用方案 A：掘金只补 `2018-01-01 ~ 2020-12-31`；米筐先修股票池过滤，再重写 `2018-01-01 ~ 2021-12-31`。用户补充要求：DDB 查询次数不能太多，优先一次性或少批次全量获取；DDB 路线可以先全量查询再在本地筛选股票数据，以减少对数据库的请求次数；如果 DDB 入库数据本身有问题，可以改用米筐官方接口，但官方接口的股票代码通常是必选项，实施复杂度更高。

## 目标范围

### 掘金数据

补齐以下目录的 `2018-01-01 ~ 2020-12-31` 数据，不主动覆盖现有 2021 数据：

- `gm_stock_all_data`
- `15min_stock_data_dir`
- `15min_stock_data_right_dir`

日线和分钟线都以现有 schema 写入，保持 `code` 为 `SZSE.000001` / `SHSE.600000` 这类本地 GM 格式。

### 米筐数据

修复股票池过滤后，重写以下目录的 `2018-01-01 ~ 2021-12-31` 数据：

- `rq_stock_all_data`
- `rq_adj`

重写目标是清除现有 2021 的指数/节假日污染，并补齐 2018-2020。米筐 15 分钟目录 `rq_15min_stock_data_dir` 暂不纳入本次主线，因为当前 `米筐数据更新.py` 已有 `fetch_minute_full` 但主流程未接入分钟线写入；若后续需要米筐分钟历史，应单独设计，避免把日线补数和大规模分钟补数混在一起。

## 数据源策略

### DDB 优先，但先过质量门

米筐主路径优先使用 DDB，因为现有脚本已经围绕 DDB 构建，且可以低查询次数批量获取。执行大范围重写前，先做小样本质量门：

- 用 DDB 查询 `2018-01-02`、`2021-01-04`、`2021-02-11`、`2021-10-04` 等样本。
- 样本日必须只返回 `instrument_base.type='CS'` 股票。
- 交易日样本不得出现 `SHSE.000001`、`SHSE.H50066`、`SZSE.980001` 等非股票代码。
- A 股节假日样本应返回 0 行。
- 与现有掘金样本或米筐官方接口样本做数量级和字段 sanity check，允许股票池口径略有差异，但不能存在系统性污染。

质量门通过后才执行 DDB 历史重写。

### 控制 DDB 查询次数

DDB 历史重写不按天循环查询。设计上采用“按大区间批量拉取，优先保护数据库请求次数”的原则：

- 优先一次性覆盖 `2018-01-01 ~ 2021-12-31` 的日线、ST、股本、复权因子、名称数据。
- 如果一次性查询触发 DDB 超时或内存压力，则退到按年份批量，每年一批；不退到按日查询。
- 每个批次内部仍保持低查询次数，目标是沿用或改造现有 `fetch_day_range` 的多表批量查询模式，而不是每日循环。
- 股票池过滤可以采用“DDB 全量查询 + 本地过滤”的方式：每个大批次先从 DDB 拉取后缀为 `.XSHE/.XSHG` 的行情，再用同批次取到的 `instrument_base where type='CS'` 股票池在 Polars 中过滤。这样会多传输一部分指数/非股票数据，但能避免把 5000 多只股票代码拆成大量 DDB 查询。
- 如果全量后本地过滤的数据量过大，再考虑 DDB 侧半连接过滤；不把“SQL 层过滤”作为默认前提。

### DDB 不可信时切换官方接口

如果质量门显示 DDB 入库数据本身存在系统性问题，例如股票日线价格、复权因子、股本字段与官方米筐样本明显不一致，则暂停 DDB 全量重写，改走米筐官方接口方案：

- 使用 `my_utils/rqdata.py` 中的官方 `rqdatac` 能力或新增受控官方接口入口。
- 官方接口大概率要求显式传入股票代码，因此需要先获取历史股票池，再按股票批次和日期区间分块请求；不能像 DDB 一样简单全市场无代码拉取。
- 先按少量交易日验证字段和 schema。
- 再按较大时间片拉取并写入 `rq_stock_all_data` 和 `rq_adj`。

官方接口方案作为 fallback，不在 DDB 质量门通过时启用。

## 代码设计

### `任务/数据更新v2.py`

保留日常增量行为，新增历史补数能力：

- 增加 CLI 参数：`--start-date`、`--end-date`、`--mode insert|update`、`--skip-day`、`--skip-min`、`--min-align left|right|both`。
- 默认参数保持日常增量兼容，不改变 `run_update_data.bat` 的现有行为。
- `update` 模式对指定日期范围做覆盖写入：写入前只清理目标日期分区，避免影响范围外数据。
- 分钟线根据日线股票池逐日更新，但只处理指定范围内缺失或被要求覆盖的日期。
- 日志写入 `log/数据更新v2.log`。

### `任务/米筐数据更新.py`

保留日常增量入口，修复并增强历史重写：

- 修复 `fetch_day_range` 中 `rq_codes` 未生效的问题，在 DDB 查询源头过滤 `instrument_base.type='CS'` 股票。
- 增加质量门函数，用少量样本检查 DDB 源是否包含非股票、节假日污染和明显字段异常。
- 支持大范围 `--mode update --start-date 2018-01-01 --end-date 2021-12-31` 重写。
- 增加可选批次参数，例如 `--batch-mode all|year|days` 或 `--batch-size`，默认历史补数优先使用大范围批量，减少 DDB 查询次数。
- DDB 查询默认允许先全量取 `.XSHE/.XSHG` 后缀数据，再在 Polars 中用 `instrument_base.type='CS'` 股票池过滤；仅在全量结果过大时切换到 DDB 半连接过滤。
- `update` 模式继续使用 `write_partitioned` 清理目标日期分区后写入，避免新旧文件叠加。
- 日志写入 `log/米筐数据更新.log`。

### `my_utils/rq_fun.py`

优先复用已有 schema、日期、分区写入函数。若需要增强，只做向后兼容的小改动：

- 复用 `RQ_DAY_SCHEMA`、`RQ_ADJ_SCHEMA`、`write_partitioned`、`get_existing_dates`。
- 如需支持“清理范围内已有但新数据为空的异常节假日分区”，新增范围清理工具函数，并只在 `mode='update'` 的明确范围内调用。

## 执行流程

1. 运行米筐 DDB 质量门，只做少量样本查询。
2. 若 DDB 质量门通过，修复脚本并执行米筐 `2018-01-01 ~ 2021-12-31` 大范围重写。
3. 若 DDB 质量门失败，暂停 DDB 全量重写，切换官方米筐接口方案并重新验证样本。
4. 执行掘金 `2018-01-01 ~ 2020-12-31` 日线补数。
5. 执行掘金 `2018-01-01 ~ 2020-12-31` 左对齐和右对齐 15 分钟补数。
6. 汇总验证覆盖范围、样本字段、异常代码、节假日分区和日志结果。

## 验证标准

补数完成后必须验证：

- `gm_stock_all_data` 的最早分区不晚于 `2018-01-02`，并覆盖 2018-2020 交易日。
- `15min_stock_data_dir` 和 `15min_stock_data_right_dir` 覆盖同一批 2018-2020 交易日。
- `rq_stock_all_data` 和 `rq_adj` 的最早分区不晚于 `2018-01-02`，并覆盖 2018-2021 交易日。
- `rq_stock_all_data` 在 `2021-02-11`、`2021-10-04` 这类 A 股节假日没有非股票分区数据。
- `rq_stock_all_data` 在样本交易日不包含 `SHSE.000001`、`SHSE.H50066`、`SZSE.980001`。
- 样本交易日的 schema 与 `RQ_DAY_SCHEMA` / `RQ_ADJ_SCHEMA` 对齐。
- 日志中没有 DDB 超时、接口认证失败、写入失败、schema cast 失败等错误。

## 风险与边界

- 掘金分钟历史补数数据量很大，耗时可能远超日线；应分年或分月执行，并在每个阶段做可恢复验证。
- DDB 一次性全量查询可能内存压力较大；如果失败，只降级到按年批量，不采用按日查询。
- 米筐和掘金股票池口径存在差异，例如 B 股、退市股处理不同；验证时关注污染和字段正确性，不要求两源每日股票数量完全一致。
- 本设计不清理 `run_update_data.bat` 的日常增量流程，避免影响当前定时任务。
- 不重写掘金 2021，除非后续验证发现掘金 2021 也存在系统性问题并得到用户确认。

## 用户确认

用户已确认方案 A，并补充：

- 如果米筐 DDB 数据整体有问题，可能需要全量复写。
- DDB 查询次数不能太多，最好一次性全量获取。
- DDB 查询时可以一次性全量查询后再筛选股票数据，查询次数优先于 SQL 层精细过滤。
- 如果 DDB 入库数据有问题，可以直接用米筐官方接口查询。
- 米筐官方接口查询更麻烦，因为股票代码大概率是必选项，需要先准备股票池再分批请求。

本设计将这些约束作为实施前置条件和 fallback 策略。
